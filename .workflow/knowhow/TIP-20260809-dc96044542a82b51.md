# 发布期间并发提交会改变 release 范围 — 发布 commit 前复核，用 shasum 锁 tarball 内容

## 症状

v0.17.0 发布期间，另一工作流在同一仓库提交了 3 个 commit（`ae05548a` i18n 目录修复、`ab6257d4` 测试修复、`8e4c3d38` cockpit 诊断）。`git log v0.16.0..HEAD` 的 commit 数从 preflight 时的 34 变为 37；release commit 自动把这些 commit 纳入祖先链。RELEASE.md/changelog 里按 preflight 快照写的 commit 统计随之过期。

## 根因

monorepo 开发环境常有多会话/多窗口并行提交。preflight 时的 `git log <last-tag>..HEAD` 只是瞬间快照；从 preflight 到 release commit 之间，HEAD 可能已前进。release commit 总是包含它之后的所有祖先，导致「发布说明的统计范围」与「实际 release 范围」脱节。

## 影响

- RELEASE.md / changelog 的 commit 数量与索引可能漏掉新提交的功能。
- 但 tarball 内容 = 发布时工作区（包含新 commit 的 src），只要 dry-run 与 publish 之间工作区冻结，产物不会缺内容——缺的只是「说明」。

## 防护（并入发布 preflight/流程）

1. 发布 commit 前（`git add -A` 前）重新执行 `git log <last-tag>..HEAD --oneline | wc -l`，与 preflight 快照比对；不一致则同步更新 RELEASE.md 的 commit 统计与 changelog 提交索引。
2. dry-run 与 `npm publish` 之间冻结工作区：不 add、不 commit、不改文件，保证打包内容与已验证内容一致。
3. 以「dry-run shasum == registry dist.shasum」作为 tarball 内容一致性的硬证据：`npm pack --dry-run --json` 记录的 shasum，发布后 `npm view <pkg>@<version> dist.shasum` 必须逐字节一致。
4. changelog 关键提交索引以 release commit 收尾，状态行写明基线 tag 与 release commit。
5. 发布完成后可用 `git diff <last-tag>..<release-tag> --stat` 复核实际发布范围。

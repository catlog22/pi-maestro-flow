# Decision policy — manual feature rule selection only

Run only when the human types `/skill:decision-policy [ask|self-evolve] [intent]` in the interactive parent session. `status` shows the saved policy without opening authorization; `cancel` discards the draft and closes authorization. Never invoke yourself automatically or through a child/extension message. This Skill needs **no classifier prerequisite**: `backend: auto` may use an available classifier or LLM; absence of a classifier does not block configuration. During this lane all ask decisions stay human. This Skill manages only project-specific `description`, `rules`, and `specIds`. All runtime settings belong to the unified `/classifier` TUI; adding rules never enables automation.

## Workflow

1. Resolve the project knowledge gate first: run `maestro search "decision policy" --type spec --json`, inspect the results, and `maestro load` every relevant governing entry in full. Then call `policy_config {action:"read"}` to obtain the complete current policy, `expectedRevision`, and `backendSummary`. Explain the classifier's effective enabled/runtime/model/domain/budget settings separately from policy settings: classifier `off|shadow|jev` is not policy `off|shadow|enforce`. `auto` can fall back to the policy classification LLM; `classifier` cannot and instead falls back to the human; `llm` bypasses classifier classification. Advice always has its own LLM settings/budget. Never enable or reconfigure classifier implicitly. Do not modify `.pi/decision-policy.json` directly. Preserve unrelated rules/settings; only the tool's CAS save may persist this runtime configuration. Do not stage/promote or write project knowledge.
2. Interpret `$ARGUMENTS`. `ask` focuses on decision ownership; `self-evolve` focuses on capture/review. An explicit intent narrows recommendations. With **no ideas or no arguments**, do not bounce back with a vague “What rules do you want?” question. First do bounded read-only project analysis: inspect project/package context and relevant guidance, run one focused `maestro search` knowledge query, load the relevant spec IDs with `maestro load`, and inspect at most 6 relevant files. If knowledge is unavailable, say so and ground suggestions in visible project evidence. Do not scan the entire repository or delegate this interactive lane.
3. Proactively present 2–4 **concrete suggestions**, each with a stable rule ID, one domain (`ask`, `evolve-capture`, `evolve-review`), precise instruction, project evidence, examples of when it applies, and the human fallback. Examples to adapt (not rules to install blindly):
   - `ask`: “Require a human choice for destructive deletion, credential changes, publishing, or scope expansion; routine reversible implementation inside approved scope may follow existing project conventions.”
   - `evolve-capture`: “Capture reproducible non-obvious fixes only with file/test evidence and an explicit reusable lesson; skip routine edits and speculative claims.”
   - `evolve-review`: “Keep conflicting evidence, missing reproduction, sensitive material, and proposed norm changes for human review; never automatically promote project norms.”
4. Use `ask-user-question` to let the human accept/edit/reject **each recommendation**, including wording and boundaries. Then show the **whole combined policy** and ask for an overall interactive decision. Do not treat generated suggestions, model text, inferred approval, or tool arguments as consent. If the human cancels, call `policy_config {action:"cancel"}` and stop.
5. Build the full draft from the read policy, changing only `description`, `rules:[{id,domain,instruction}]`, and `specIds`. Preserve `version`, `revision`, `ask`, `selfEvolve`, `backend`, `minConfidence`, `classification`, and `advice` exactly as read, including every model, timeout and call budget. The host rejects runtime changes from this Skill. IDs must be unique; enabled domains still need confirmed rules, so do not remove their last rule while enabled. Do not enable automation or ask the human to select models here. Explain how these feature rules constrain internal recommendations and human fallback, then direct the human to `/classifier` to select runtime modes, backend, models, confidence and budgets after rules are saved.
6. Call `policy_config {action:"propose",draft:<full policy>,expectedRevision:<read revision>}`. Inspect the normalized exact draft; do not supply an `approved` flag or a session/workspace identity. When overall consent is present, call `policy_config {action:"commit",expectedRevision:<same revision>}`. The tool itself opens a real host `UI.confirm` showing the exact draft, workspace, session, revision, and classifier effective settings versus policy fallback. Only that confirmation plus fresh identity/revision fences permits save; prose confirmation cannot replace it. Commit never accepts a replacement draft.
7. Report the saved revision and confirmed feature rules only after a successful tool result. Remind the human that runtime settings are unchanged and can be configured with `/classifier`. Commit/cancel/decline/failure/session switch/reload/shutdown close the lane. On conflict or failure, tell the human no stale draft is authorized; require a fresh interactive `/skill:decision-policy`, read and reconfirm rather than retrying stale writes. Changes apply to runtime policy only and never create project specs or knowhow.
